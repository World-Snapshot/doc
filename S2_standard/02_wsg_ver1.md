## Overview
WSG (World Snapshot Graphics) is a high-dimensional image format that extends traditional RGB images with additional channels to store rich metadata at the pixel level. Each pixel in a WSG file contains 256 channels of floating-point data.

Generally speaking:

1. I set -1 as the mask area, representing non-existence. 0 represents False, and 1 represents existence or True. WSG should be able to be read and trained in the NPZ format, as this is the most common format for AI and it has a strong compression capability for repeat number (eg., -1.) If a value represents a range and includes -1, it should be emphasized. During training, special adjustments are made to avoid masking this area.
2. The indentation relationship represents the loop/subordinate relationship.
3. Regarding the optional format standards, we have not conducted in-depth trials and do not have corresponding WSG file samples. They are merely recommended. We may calibrate them in future WSG minor version updates.
4. For the channels that are very significant for the original data, we could normalize them in advance to prevent any interference with them during future training. Although in general, we will restore them back to their original state when generating the final results.
5. Since the npz format requires the same data type, considering the storage issue, I decided to use float16 as the format for storing our WSG. When training the model and loading it later, we may be able to use bf16 or float32 at that time. Additionally, float16 seems unable to represent a large number of digits such as 100,000. Therefore, IDs and the like must not exceed 100,000. They can be replaced by using 1 (True) and 0 (False). Always keep in mind to optimize the logic and structure of WSG.

### Quantum Phase Field [8-15] (Necessary) (Encodable control domain)
- 8: Wave Function ID
- 9: Wave Phase  
- 10: Angular Frequency ($\omega$)
- 11: Basic Decay ($d_0$)
- 12-15: Reserved for future expansion

**Note:** Initially, I planned to encode some information into the frequency of the wave using the frequency modulation method. This way, we wouldn't need the additional 253 channels for initialization, and the information would be closely integrated with the wave. However, 1. We ourselves need to initialize a tensor that is the same as the expected output result. At least after our reverse reasoning, we still have 256 channels. 2. If we want to change the results of the bidirectional reasoning more quickly, it would be best if we could directly input and directly modify the specific values that have not been encoded. 3. Placing the initialization information of the wave (instead of the function solution, the solution should be initialized and placed in the first four channels) into the additional channels helps us to reconstruct the wave world. 4. Encoding all the information into Wave itself will make Wave Encoder might be very difficult to train. We not only increased the burden on the Wave generator, but also increased the burden on the pixel decoder. 5. But, the drawback of new method (The method of placing all the information into an additional channel) is that 3D information is transformed into 2D information, which is prone to being obscured and confused, and it is difficult to handle the changes after interaction. Therefore, I plan to encode some invariant quantities into the waves as a double safeguard.

**Note:** For the time being, I have only designated this domain and PBR domain as being capable of being encoded, because other information is not generated along with the wave function. If the wave core space is not clean, you cannot accurately encode the corresponding properties into specific waves; artificial contamination will occur.

## Depth and Spatial Geometry Domain [32-63]
### Basic Depth & Normals [32-40] (Necessary)

- 32: Relative depth value (0-1)
- 33: Relative depth confidence (In fact, only a very small number of jobs offer this, and we are not using it for the time being.)
- 34: Absolute depth value (meters)
- 35: Absolute depth confidence (In fact, only a very small number of jobs offer this, and we are not using it for the time being.)
- 36-38: Surface normal vector (X,Y,Z)
- 39: Curvature (For a sphere, each of its positions has a curvature. It's somewhat like the 3D version of a boundary.)
- 40: Edge （False -1, True 1; -1 indicates the area of the mask, and this area is not taken into consideration at all.）

### Motion Geometry (2D optical flow, point cloud, depth)[41-56] (Necessary)
- 41: optical flow dx
- 42: optical flow dv
- 43: point cloud x
- 44: point cloud y
- 45: point cloud z
- 46: point cloud confident
- 47: world depth z
- 48: world depth confident

**Note:** We will use the world coordinates consistent with the point cloud (currently based on VGGT). If we use xy to locate pixels and z to obtain depth, this actually overlaps with the scalar depth function. It would be better for us to directly record the world coordinates of xyz here. This approach is equivalent to directly transferring the knowledge of VGGT.

**Note:** I considered using 3D optical flow with motion directions, but our camera movement and the speed of our wave space already include this information as an alternative.

## Pose and Human Information Domain [64-95]
### 2D skeletal human (DWPose) [64-71] (Necessary)
- 64: Person ID (-1 or ID number)
    - 65: Keypoint ID (about 0-134, find this keypoint based on the xy coordinates, and then mark which key point it is.)
        - 66: Score (The body score serves as an index. One person occupies 18 index values, and then the second person increments. The remaining scores represent the degree of confidence.)
- 67-71: Reserved for future 2D skeletal pose data

**Note:** The design principle for 2D skeleton poses is to define the key point ID channels, then find the corresponding pixels for the key points, and set the corresponding channels to 1/Ture. In this way, when we detect a true channel, we know that there is a key point at that location, and then we know which key point it is.

### 3D mesh human (SMPLer-X) [72-94] (Necessary)
- 72: Person ID (from bbox_id in meta dir)
    - 73: Joint ID (global_orient + left_hand_pose + right_hand_pose + jaw_pose + leye_pose + reye_pose + transl)
        - 74: Joint rotations or transl x
        - 75: Joint rotations or transl y
        - 76: Joint rotations or transl z
- 77: betas: 0 epression: 1
    - 78-87: the value of betas/epression
- 88: bbox: If the vertex is set to 1, then the absence of a vertex is naturally -1.
- 89: bbox_mmdet: If the vertex is set to 1, then the absence of a vertex is naturally -1.
- 90: vertices (vf system) id
- 91: vertices (vf system) x: it is actually the coordinates that have been calibrated based on the predicted translation information.
- 92: vertices (vf system) y: it is actually the coordinates that have been calibrated based on the predicted translation information.
- 93: vertices (vf system) z: it is actually the coordinates that have been calibrated based on the predicted translation information.
- 94: Reserved for future

**Note:** I utilized the bbox_mmdet and bbox information from Meta dir, but did not use focal and princpt, as these two elements will be provided by user.

**Note:** For 3D Mesh human models, each joint has a rotation angle. Then we use keypoint ID plus xyz rotation angles, and four channels can store this information. However, since the rotation angles do not reflect the spatial information in the image, we cannot find the corresponding pixels. We can only store this information for each pixel in the entire human body area. (This allows the model to have some sensitivity to the human body area and the large amount of information enrichment is also helpful for the already difficult 3D posture training.) If the positions of people overlap, the pixel area of this part should be given to the person with the smaller ID because this is the person that the model is most likely to detect first.

**Note:** The final rendering mainly uses the bbox (SMPLer-X box), while bbox_mmdet seems to represent smaller body areas. When saving, I use the bbox_mmdet box. Additionally, I did not store the face meshes because for SMPL, the connection relationship of its face meshes is fixed.

**More Explain:** First of all, regarding the key points, it is different from DWpose. Since it uses 3D rotation angles to represent the human body, it cannot correspond to pixels. DWpose finds corresponding key points based on xy coordinates and then stores z coordinates, but for SMPLer-X, according to the standard, we will store a piece of information throughout this area, rather than storing a certain joint point at a certain pixel. Then for pixels that obtain information in the corresponding channel, they will be marked which person they belong to, that is, person id.

For the value of each key point, we found that one pixel cannot store it completely, so we can store key point 0 and its rotation angle xyz in the first pixel, store the second key point in the second pixel, and store it evenly in the area like this. For:

- 77: betas: 0 expression: 1
- 78-87: the value of betas/expression

They follow the same logic. Betas and expression can be regarded as two types of data, each type of data has 10 values.

Then for the box vertices, if a certain pixel belongs to the box vertices, the corresponding channel is changed to 1. In this way, the model only needs to look at the corresponding channel of the entire image, and it is easy to find four points or 8 points, knowing that they are some squares.

Then for the vertices, we first find the corresponding pixel according to xy, and then put xyz into the channels 90 to 92 that we require, only put it in the corresponding single pixel, so that it has a connection with the spatial relationship. The model only needs to check the channels 90 to 92 of all pixels, and if it finds valid information, then it is a vertex.

## Object/Animal Information [111-125] (Necessary)
- 111: Object UUID (encoded identifier)
- 112: Class Value
    - 113: Vertex ID (find this vertex based on xy coordinates, then mark which vertex it is)
        - 114: Vertex UV coordinates U
        - 115: Vertex UV coordinates V
        - 116: position Z
        - 117: skinning_weights_value (influence strength)
    - 118: Face ID (which face this pixel belongs to)
    - 119: Joint ID (joint with highest influence on this vertex)
        - 120: Joint position Z
    - 121: Bone ID
        - 122: skinning_weights_value (influence strength)
- 123-125: Reserved for future object properties

**Note:** In accordance with the usual requirements, for all pixels that contain information, at least an ID should be provided. It is also advisable to include information such as Class ID.

**Note:** Apart from normalizing the position of the pixel when searching for it, generally we do not perform any additional processing on any values.

**Note:** We respectively search for the weight values from the "skinning_weights_row" (vertex index) and "skinning_weights_col" (bone index), and then place them in the corresponding pixels. These are the necessary indices, just like key names, and the corresponding values are in the "skinning_weights_value" (weight value).

## Technical Details

### Version Control (16th channel)
Version format: MAJOR.MINOR.PATCH
- MAJOR: Breaking changes
- MINOR: New features, backward compatible 
- PATCH: Bug fixes, backward compatible

### Compatibility Requirements
- Applications must gracefully handle missing channel data (set to -1)
- RGB channels must remain viewable in standard image viewers (need develop a trick)
- Channel expansion must maintain backward compatibility
- Maintain consistent units across all files
